**Relatório semanal automático**

- `scripts/atividade.py` coleta pela API do GitHub, por pessoa: PRs abertos e
  mergeados, revisões e commits, além de PRs parados há três dias ou mais. Lê a
  semana corrente direto de `docs/cronograma.md`, sem copiar o cronograma para
  dentro do script.
- Workflow `Relatório semanal`, toda segunda às 08:00 de Brasília: roda o script,
  entrega os números ao assistente para a leitura da semana, e abre PR com o
  relatório. Também roda sob demanda.

**GitBook x proteção da `main`**

- O erro do GitBook foi diagnosticado pela API: o Git Sync do espaço
  `Documentação` apontava para a `main` e a operação que falhou era de
  **exportação** — o GitBook tentando escrever no GitHub, barrado pelos dois
  rulesets.
- Ficou claro que, enquanto o Git Sync apontava para a `main`, **o GitBook era
  uma porta dos fundos**: qualquer pessoa com acesso de edição ao site escrevia
  na `main` sem PR, sem revisão e sem passar pelo líder. A trava não quebrou o
  fluxo, expôs um furo que já existia.
- Criada a branch permanente `gitbook/docs/documentacao`, a partir da `main`.
- Workflow `gitbook-sync.yml` fecha o ciclo nos dois sentidos, sem trabalho
  manual: edição no site vira PR para a `main`; merge na `main` volta para a
  branch do GitBook.
- Revisões dos PRs [#1](https://github.com/Codexrocks/TCC_SDCAC/pull/1) e
  [#2](https://github.com/Codexrocks/TCC_SDCAC/pull/2) pedidas a Yasmin e Felipe.

## Decisões tomadas

| Decisão | Motivo |
|---|---|
| Branch no formato `<autor>/<tipo>/<assunto>` | O GitHub agrupa branches por prefixo. Com o autor primeiro, a lista de branches já responde "quem está com o quê" sem abrir o log |
| Lista fechada de autores no validador | Um prefixo livre não resolve nada: `xpto/docs/algo` passaria e não identificaria ninguém. A lista força o nome a ser de alguém do projeto |
| Não travar o padrão de branch por ruleset | *Branch name pattern* vale para toda branch criada no repositório, e o GitBook cria branches próprias ao editar a documentação pelo site. Travaria o Git Sync. A checagem ficou no `validar.py`, com o mesmo efeito prático |
| Merge restrito via segundo ruleset, e não pela lista de bypass do primeiro | Separar as duas coisas mantém `Proteção da main` sem bypass nenhum. O Davi ganha o direito de **executar** o merge, e continua obrigado a PR, aprovação de outra pessoa e check verde |
| Bypass por `OrganizationAdmin`, não por usuário | Davi é o único owner da organização. A regra fica amarrada ao papel, não a uma conta — se a liderança mudar, muda o papel, não o ruleset |
| Registrar o problema de acessibilidade sem alterar `arquitetura.md` | As faixas e pesos são da Yasmin. A correção proposta é de apresentação e fica em `usabilidade.md` até ela decidir |
| Python 3.12, e não a mais recente | `pandas` e `scikit-learn` costumam demorar a ter pacote pronto para as versões mais novas, e a instalação passa a compilar da fonte. A 3.12 é a mais segura para esta stack |
| `[tool.setuptools] packages = []` no `pyproject.toml` | Permite `pip install -e ".[dev]"` funcionar hoje, sem código nenhum e sem criar pasta vazia, que o `CLAUDE.md` proíbe |
| Relatório semanal em duas etapas — script conta, assistente interpreta | Número de relatório de banca precisa ser reproduzível. Com a contagem num script sem IA, qualquer número pode ser conferido rodando o comando |
| Instruir o workflow a não inventar número | Semana vazia é resultado válido. Relatório automático que enfeita número é pior que relatório nenhum, porque a banca confia nele |
| Marcar `<!-- FALTA CITAÇÃO -->` em três pontos de `usabilidade.md` | Porcentagem de Nielsen e Landauer, limites das faixas adjetivas do SUS e edição de Shneiderman precisam ser conferidos na fonte. O `CLAUDE.md` proíbe inventar dado acadêmico |
| Guia do GitHub como página própria, e não só como comentário no PR | Yasmin precisa do passo a passo agora, para aprovar o PR #1 — mas vai precisar de novo toda semana. Comentário some no meio do thread; página fica no GitBook e serve também para o Felipe |
| GitBook em branch dedicada, e não com bypass no ruleset | Dar bypass ao app do GitBook faria o site voltar a funcionar em um minuto, mas devolveria a porta dos fundos: a equipe toda tem acesso ao GitBook, e cada edição entraria na `main` sem revisão. A branch dedicada mantém a edição pelo navegador e o conteúdo continua entrando por PR |
| Automatizar os dois sentidos da sincronização | O trabalho manual recorrente era o único ponto fraco da branch dedicada. Com o workflow, ninguém precisa lembrar de abrir PR nem de trazer a `main` de volta — e branch que ninguém atualiza diverge em poucos dias |
| Corpo do PR automático num arquivo, e não em heredoc no workflow | Heredoc dentro de bloco `run:` quebra o YAML pela indentação. Em arquivo separado, o corpo também fica revisável |
| `gitbook` entra na lista de autores do validador | A branch precisa passar no check `validar` para o PR fechar. Ficou registrado no código que não é pessoa, e que a branch não se apaga |
| Rodar a validação em todo PR, não só nos que miram a `main` | O PR #2 abriu sem check nenhum e ficou mergeável na hora. Restrito a `branches: [main]`, o gatilho deixava PR empilhado passar sem conferência — e os rulesets só protegem a branch padrão |
