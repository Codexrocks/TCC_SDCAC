## O que foi respondido / feito

### O artigo ganhou lugar próprio

A pergunta que abriu a sessão não era sobre GitBook, era sobre pessoas: **oito
das quinze semanas do cronograma são prosa, não código.** Yasmin e Felipe vão
escrever muito mais do que vão programar. Exigir que passem por branch, commit
e Pull Request para redigir um parágrafo é barreira sem contrapartida.

Mas a `docs/` está fechada para escrita desde a sessão 06, com bom motivo: o
GitBook reformata o que toca, e o conteúdo técnico não sobrevive.

A saída foi separar os dois mundos:

| Diretório | Espaço no GitBook | Quem escreve | Por quê |
|---|---|---|---|
| `docs/` | *TCC_SDCAC Docs* | GitHub, só leitura no GitBook | Normalização destrói tabela, comentário e quebra de linha |
| `artigo/` | *Artigo* (a criar) | **GitBook, escrita liberada** | Prosa corrida sobrevive à normalização sem prejuízo |

A restrição do produto obrigou a esse desenho, não a preferência: **espaços do
GitBook não podem ter raízes aninhadas.** `artigo/` precisou nascer irmão de
`docs/`, e não dentro dele.

Criados: `artigo/README.md`, `SUMMARY.md`, `.gitbook.yaml` e os cinco capítulos
(`01-introducao` a `05-conclusao`) mais `referencias.md`. **Todos são esqueleto
com instruções — nenhuma linha de conteúdo acadêmico foi inventada.**

As diretrizes institucionais do PDF viraram [`docs/diretrizes.md`](../diretrizes.md),
com ABNT e abstract em inglês confirmados pelo Davi.

### O primeiro Pull Request de outra pessoa — e o que ele revelou

Às 14:17 o Felipe abriu o [PR #5](https://github.com/Codexrocks/TCC_SDCAC/pull/5),
preenchendo a linha dele em `uso-de-ia.md`. **O conteúdo estava certo.** Três
coisas em volta não estavam, e nenhuma era culpa dele:

1. **Branch `FilipeF4guiar-patch-1` e commit `Update uso-de-ia.md`.** O guia
   dizia *"nome da branch: `felipe/docs/assunto`"* como se o campo estivesse
   vazio esperando ser preenchido. Não está — o GitHub já o entrega com um nome
   que reprova, e é preciso apagar por cima. Isso não estava escrito em lugar
   nenhum.
2. **A seção Uso de IA ficou com os comentários do modelo.** As linhas entre
   `<!--` e `-->` são instrução, não resposta, e somem quando o PR é exibido.
3. **O check `governanca` aprovou mesmo assim** — e esse é o achado grave.

O terceiro item virou investigação. O GitHub devolve o corpo do Pull Request com
**CRLF**. Depois de remover os comentários, o campo vazio ficava assim:

```
- **IA usada:**  \r
```

E `\r` não é removido por `.strip(" *_`-")`. O campo em branco parecia
preenchido. **A verificação de declaração de IA estava aprovando template
intacto desde que foi escrita** — só ninguém tinha aberto um PR pela interface
do GitHub para descobrir.

Os testes não pegaram porque as strings de teste foram escritas à mão, com `\n`
puro. Corrigido em `sem_comentarios`, com cinco casos novos no formato real, e
verificado que eles **falham** se a normalização for removida.

### O gancho e o guia

Dois tropeços com a mesma raiz — a ferramenta mais rígida que a regra que ela
imita:

- O gancho `commit-msg` barrava commit de merge pedindo `Assistido-por:`, sendo
  que o `validar.py` usa `--no-merges` e ignora esses commits desde sempre.
  Agora ele sai antes quando existe `MERGE_HEAD`.
- O [Guia do GitHub](../guia-github.md) passou a mostrar lado a lado **o que vem
  preenchido** e **o que escrever por cima**.

### A governança travava a si mesma

O Davi não conseguiu mergear o PR #3 mesmo com tudo aprovado. A causa não era
regra do projeto, era mecânica do GitHub:

**Check runs de mesmo nome se acumulam no mesmo commit.** O workflow da
governança roda de novo a cada revisão enviada, sempre no mesmo commit, e o
caminho normal é reprovar primeiro (sem aprovação) e passar depois (com as
aprovações). A reprovação antiga continuava contando, e o rollup ficava
`FAILURE` com tudo verde na tela.

A correção estrutural: o resultado passou a ser publicado como **commit status**,
que a documentação do GitHub define como

> success if the latest status for all contexts is success

— vale o mais recente por contexto, e o histórico não atrapalha.

O job foi renomeado de `governanca` para **`verificar`**, e o status publicado
chama-se **`governanca`**. Os dois precisam de nomes diferentes: quando um check
e um status compartilham o nome, o GitHub exige que **ambos** passem, e o check
run voltaria a travar tudo.

Verificado no commit `8291b05`: o rollup passou a trazer `verificar` (check run,
não obrigatório), `validar` (check run, obrigatório) e `governanca`
(**StatusContext**, obrigatório), publicado por `github-actions[bot]`. Nenhum
check run fantasma chamado `governanca` sobrou esperando.

### Limpeza

Cinco branches apagadas. Restaram quatro: `main`, a do PR aberto e as duas do
GitBook.

Descoberta pelo caminho: `git merge-base --is-ancestor` **nunca** confirma que
uma branch foi mergeada neste repositório, porque o merge é sempre *squash* e o
commit original não vira ancestral de nada. A conferência passou a usar o estado
do Pull Request.

## Decisões tomadas

| Decisão | Motivo |
|---|---|
| Artigo em espaço próprio, com escrita liberada no GitBook | Oito das quinze semanas são prosa; obrigar quem escreve a usar Git é barreira sem contrapartida |
| `artigo/` irmão de `docs/`, não dentro | Espaços do GitBook não aceitam raízes aninhadas — restrição do produto, não escolha |
| `docs/` continua só leitura | A normalização do GitBook destrói tabela, comentário e quebra de linha |
| Capítulos entram como esqueleto, sem conteúdo | Regra 5: não inventar conteúdo acadêmico. O texto é de quem assina |
| Governança vira commit status, não check run | Check run acumula resultados no mesmo commit; status vale pelo mais recente |
| Job renomeado para `verificar` | Nome igual entre check e status faz o GitHub exigir os dois |
| `verificar` **não** entra nos checks obrigatórios | Ele acumula falhas por natureza; quem decide é o status |
| Não recriar o PR do Felipe por conta própria | A autoria é dele, e a declaração de IA precisa das respostas dele |
| Conferir merge pelo estado do PR, não por ancestralidade | *Squash* apaga a linhagem do commit original |

> **O comentário estava certo e mesmo assim foi o texto errado.** Ele explicava
> a causa, assumia a culpa do guia e admitia o defeito do check — tudo
> verdadeiro. Mas tinha três seções e uma tabela, e chegou como resposta ao
> primeiro Pull Request de alguém que nunca tinha usado GitHub. **O volume de
> correção sinaliza gravidade mesmo quando cada frase nega que seja grave.**
>
> É o erro mais relevante da sessão para o artigo, porque nenhuma automação
> deste repositório o teria pego: não há check para tom.

> **O erro do CRLF é o retrato do limite dos testes escritos pela mesma IA que
> escreve o código.** Ela inventa a entrada, e inventa uma entrada que o código
> dela já trata. É o mesmo padrão do `command -v python3` na sessão anterior:
> só o dado real reprova.
